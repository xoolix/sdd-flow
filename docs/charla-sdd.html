Disciplina

Ingeniería de la Ventana de Contexto

1Más tokens no es mejor — la relevancia supera al volumen
2Chat largo + MCPs innecesarios saturan la ventana
3Los LLMs son funciones stateless. Solo existen los tokens actuales.

La ventana es finita. Cada token que desperdicias es contexto que perdés.

Fundamentos

Qué es un LLM (en 30 segundos)

  • Un modelo predice el siguiente token en base a los tokens anteriores
  • No "entiende" — calcula la continuación más probable
  • No tiene curiosidad. No pregunta por límites.
  • Generar buen código ≠ construir un producto de software

La tesis

La tesis de SDD

Sin SDD

"haceme X" → modelo improvisa → código sin spec → no hay review → "ya está" (?)

Con SDD

/new-feature → spec.md → /plan-feature → plan.md + tasks.md → /implement-task → /review-feature → /archive-feature

SDD = el modelo codifica solo lo que está especificado, y se valida que lo hizo bien.

Diseño

Principios de diseño de SDD

  • Spec primero — Si no está escrito, no se implementa
  • El humano decide, el modelo ejecuta
  • Fases con artefactos — cada paso produce un archivo
  • Validación automática — lint, tests, review
  • Retry con feedback (max 2)
  • Escalation, no loops infinitos
  • Sesiones aisladas — prevención de la Dumb Zone

Fase 1: Spec & Research

Modelo: Opus
Humano
↔
Orchestrator (Opus)
→
spec.md

El objetivo NO es escribir código. Es modelar el dominio y definir el problema. El modelo hace preguntas guiadas para definir:

  • Triggers de la funcionalidad
  • Happy paths y dominios afectados
  • Criterios de Aceptación (Given/When/Then)
👤 Pausa Humana: el desarrollador dicta la arquitectura y aprueba el spec antes de avanzar.

Sub-agentes exploradores escanean el repositorio. Un evaluador filtra dependencias de alto impacto y descarta código irrelevante.

🧠 Alineación Mental: el humano lee el plan, no 1,000 líneas de código. Esto asegura que todo el equipo entiende cómo va a cambiar el sistema antes de que el código exista.

Fase 3: Implementación Aislada

Modelo: Sonnet
plan.md
tasks.md
→
Implementa 1 tarea
→
Validación (lint, tests)
→
Pass ✓
Fail → Corrección Autónoma (max 3) → retry

Lee plan.md para entender el diseño y tasks.md para saber exactamente qué implementar. Sesión completamente nueva por tarea. Ventana limitada estrictamente a la tarea actual.

  • El modelo no decide qué hacer — ejecuta lo que el plan dice
  • Validación inline automática después de cada cambio
  • Divergencias documentadas en decisions.md
🔒 Sesión limpia: cada tarea arranca de cero. El código basura de una tarea anterior nunca contamina la siguiente.

Modelo: Sonnet x3 + 1 Adversarial

3 agentes independientes evalúan el código contra los criterios Given/When/Then. Un solo voto de fallo rechaza. Un cuarto agente ataca las premisas, no el código:

  • Busca edge cases olvidados
  • Detecta asunciones no documentadas
  • Encuentra brechas de seguridad funcionales
👤 Pausa Humana: revisión exclusiva de Gaps Críticos (SPEC-GAP-HIGH). El código no se integra a ciegas.

Fase 5: Archive

Modelo: Haiku

Cierre formal de la feature. Deltas de decisions.md se fusionan en el spec final. Todo se mueve a specs/archive/.

  • Merge de delta specs en spec.md final
  • Mover carpeta a specs/archive/
  • Todo queda en git, auditable, reproducible

Base de Datos Engram

El Problema: Al crear sesiones nuevas para proteger la ventana, el LLM sufre de amnesia.

La Solución: Engram actúa como el hipocampo del sistema.

Funciones Clave:

  • Registra decisiones de negocio y deltas arquitectónicos.
  • Un feature pausado y retomado en un mes mantiene el 100% de su contexto histórico.

Sesiones efímeras, memoria permanente.

CLAUDE.md

El cerebro del orquestador. Pipeline, model routing, reglas de delegación.

rules/

Convenciones del equipo. Se inyectan automáticamente en cada sesión.

skills/

Cada fase del pipeline es un skill. Prompt reutilizable con instrucciones precisas.

specs/

Cada feature tiene su carpeta. spec → plan → tasks → decisions. Todo queda en git.

Reglas de oro

Reglas de Oro

1. Protege tu Ventana

Cada token importa. No contamines la ventana de contexto.

2. El Código es Contexto

Tu código existente es lo que el modelo lee. Basura in, basura out.

3. Planea y Comprime

Sesiones cortas. Estado en archivos. Memoria persistente.

4. No Subcontrates el Pensamiento

Delega ejecución, nunca la decisión.

"La parte mecánica se murió.
La ingeniería nunca fue tan importante."

Entiende el problema, modela el dominio y haz las preguntas que el modelo ni siquiera sabe que ignora.
